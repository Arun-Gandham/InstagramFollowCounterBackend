# Security Threat Model: Physical Instagram Follower Counter Backend

**Date:** September 14, 2026  
**System Classification:** Commercial IoT Backend & OAuth Integration Platform

---

## Threat Analysis Matrix

| # | Threat Scenario | Risk Level | Mitigation in Architecture | Residual Risk & Operational Guidance |
|---|---|---|---|---|
| 1 | **Database Stolen (Dump Leak)** | CRITICAL | All Instagram access tokens and refresh tokens are encrypted at rest using **AES-256-GCM** with master keys stored strictly outside the database in environment/secret storage. Passwords use ASP.NET Core Identity PBKDF2/Argon2 hashing. Device secrets and claim codes are stored only as SHA-256 hashes. Plaintext secrets are never stored. | Attacker gains user emails and usernames, but cannot access Meta accounts or impersonate devices without the external encryption master key. |
| 2 | **Server Compromised (RCE / Host Access)** | CRITICAL | Non-root Docker execution, read-only file systems where feasible, strict OS firewall blocking external PostgreSQL access, separate key management, minimal attack surface (no microservices/Kubernetes/Kafka). | If the process memory is dumped while active, currently decrypted tokens in active worker memory could be exposed. Mitigated by short runtime scope and immediate disposal. |
| 3 | **Instagram Access Token Stolen** | HIGH | Tokens are never returned to browsers or hardware devices. Tokens reside in memory only during active external API calls. Decryption occurs strictly inside `ISecretProtector`. If a token is compromised, Meta allows instant revocation via account settings. | Tokens could be abused until revoked or expired (60-day limit). Reauthorizing invalidates all prior tokens. |
| 4 | **OAuth CSRF** | HIGH | OAuth `state` parameter is a cryptographically secure 256-bit random token. Stored hashed (SHA-256) in `InstagramOAuthSessions`, bound to the authenticated user ID with a 10-minute expiration. Verified with constant-time comparison and invalidated immediately upon first use. | None. Attacker cannot craft a valid state parameter for another user. |
| 5 | **OAuth Code Interception** | MEDIUM | Authorization codes are single-use by Meta. Code is sent strictly to our HTTPS redirect URI and exchanged server-to-server with `client_secret`. Frontend never handles codes. Trailing `#_` stripped cleanly. | MITM or malicious redirect URI injection prevented by strict exact redirect URI registration in Meta App Dashboard. |
| 6 | **Claim QR Code Photographed in Transit / Unboxing** | MEDIUM | Claim codes are distinct from device credentials. Claim codes are single-use, time-limited, and stored as SHA-256 hashes. Once a customer claims the device, the claim code is permanently invalidated. Double-claiming is rejected by database-level concurrency. | If someone opens the retail box before customer delivery and claims it, the customer will see an "Already Claimed" error and can contact support. Support can re-issue claims after verifying purchase receipt. |
| 7 | **Physical Device Stolen** | MEDIUM | Physical devices hold only their individual device secret. The device firmware never receives or stores user passwords, email, Meta Client Secret, or Instagram access tokens. | Thief can poll the follower count for the linked Instagram account. Owner can unbind or disable the device immediately from the customer web portal. |
| 8 | **Device Cloned** | MEDIUM | Device secrets are 256-bit high-entropy cryptographically random strings generated during manufacturing. Hashed in database. Constant-time comparison prevents timing attacks. Disabling the device in admin portal terminates access immediately. | Attacker would need physical flash chip readout or hardware debugging access to clone the single device secret. Hardware secure element / flash encryption recommended for firmware. |
| 9 | **Brute-Force Login & Credential Stuffing** | HIGH | Built-in ASP.NET Core rate limiting (strict IP and user rate limits), account lockout (5 failed attempts locks account for 15 minutes), constant-time password hash evaluation. Email verification required before login. | Distributed botnets could attempt low-velocity distributed brute force. Can be further mitigated by Cloudflare/WAF challenge. |
| 10 | **Token Replay** | MEDIUM | Claim tokens and OAuth state tokens are strictly single-use. Once `UsedAt` is recorded in a database transaction, subsequent requests fail immediately. | None. Transaction rollback prevents partial state changes. |
| 11 | **Device Secret Leaked** | HIGH | Admin portal can disable or revoke any compromised device immediately (`DeviceStatus.Revoked`). Database stores only `CredentialHash` so database leaks do not expose device secrets. | Device must be reprovisioned or decommissioned if secret is extracted from firmware. |
| 12 | **Admin Account Compromise** | CRITICAL | Admin role is isolated. Admin endpoints require explicit `Roles = "Admin"`. Audit logs record all administrative actions with timestamp, IP hash, and correlation ID. Admin endpoints do NOT return plaintext tokens or device secrets. | Admin can view aggregate statistics and disable devices, but cannot read customer Instagram tokens or secrets. Multi-factor authentication (MFA) recommended for admin accounts in Phase 2. |
| 13 | **SQL Injection** | CRITICAL | 100% Entity Framework Core parameterized queries with Npgsql. No raw string-concatenated SQL queries in application code. | None under standard EF Core parameterized LINQ queries. |
| 14 | **XSS (Cross-Site Scripting) Impact** | HIGH | Authentication relies on server-managed `HttpOnly`, `Secure`, `SameSite=Lax` cookies. Authentication tokens are NOT accessible to JavaScript in `localStorage`. CSP headers configured via `SecurityHeadersMiddleware`. | If XSS occurs in frontend, attacker cannot steal auth cookies directly. Mitigated by anti-CSRF token protection on state-changing requests. |
| 15 | **CSRF (Cross-Site Request Forgery)** | HIGH | State-changing web endpoints require Anti-Forgery tokens (`X-CSRF-TOKEN` or cookie validation). SameSite cookie policy prevents ambient browser submission from foreign origins. | Requests from third-party sites lack the custom anti-forgery header and fail validation. |
| 16 | **MITM (Man-In-The-Middle)** | HIGH | Strict HTTPS-only production configuration with HSTS (`Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`). Caddy reverse proxy enforces modern TLS 1.3/1.2. | Unencrypted HTTP traffic is rejected or upgraded automatically. |
| 17 | **Meta API Outage / Network Disruption** | MEDIUM | Resilient HTTP handling with exponential backoff and jitter. **Crucial Rule:** Follower count is NEVER reset to 0 or deleted during outages. Cached follower count is retained. Devices receive `isStale: true` while displaying last known value. | Device displays last known follower count until Meta connectivity is restored. |
| 18 | **DNS Spoofing / Hijacking** | MEDIUM | HTTPS certificate validation in typed HTTP client and reverse proxy. DNSSEC recommended on domain registrar. | Attackers cannot impersonate Meta or API endpoints without valid TLS certificates. |
| 19 | **Log Leakage of Sensitive Data** | HIGH | Structured logging with strict redaction. Tokens, passwords, verification codes, client secrets, and device credentials are explicitly excluded from log templates and sanitized in error handlers. | Accidental logging of secrets is prevented by automated unit tests validating log output hygiene. |
| 20 | **Account Takeover via Email Reset Tampering** | HIGH | Reset tokens are single-use cryptographically random Identity tokens with expiration. Password reset response is generic ("If an account exists, instructions were sent") to prevent email enumeration. | Attacker must control the customer's external email inbox to intercept the reset link. |
